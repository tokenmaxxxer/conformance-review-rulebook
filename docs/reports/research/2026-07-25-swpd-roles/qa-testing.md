# QA / Testing / Verification Roles in Software Product Development

## Roles

- **QA Engineer** — a generalist role responsible for verifying product quality via manual and/or automated methods; scope and technical depth vary widely by company. [unsourced — generic industry usage, no single canonical definition found]
- **SDET (Software Development Engineer in Test)** — a role Microsoft is credited with pioneering across the industry, combining software engineering skill with test focus (building test frameworks/automation, not just running tests) ([Gergely Orosz / LinkedIn](https://www.linkedin.com/posts/gergelyorosz_microsoft-was-the-company-to-pioneer-the-activity-7109993997468618753-s_JA), [TestGuild](https://testguild.com/sdet/)).
- **Test Engineer (TE)** — at Google, a role with a broad, less well-defined scope than SET: TEs look at the product's big picture, user impact, and risk, doing test planning, risk analysis, and manual testing while also contributing code/automation ([Google Testing Blog: Test Engineers @ Google](https://testing.googleblog.com/2013/01/test-engineers-google.html), [How Google Tests Software, ch.3](https://www.oreilly.com/library/view/how-google-tests/9780132851572/ch03.html)).
- **Test Architect** — [unsourced — term used in industry job titles/ISTQB-adjacent literature but no single authoritative definition surfaced in this research pass].
- **QA Lead** — typically a management/coordination role; ISTQB's "Test Leader"/"Test Manager" concept covers this: responsible for project management of testing activities and resources and evaluation of the test object; may be filled by a project manager, dev manager, QA manager, or dedicated test group manager ([ISTQB Foundation — Tasks of the Test Leader and Tester](https://istqbfoundation.wordpress.com/2017/09/18/tasks-of-the-test-leader-and-tester/), [ISTQB Glossary — Test Manager](https://istqb-glossary.page/test-manager/)).
- **Release QA** — [unsourced as a distinct formal title; treated in this report as the release sign-off function, see Gates section].
- **Exploratory Tester** — practitioner of exploratory testing: "simultaneous learning, test design, and test execution," as defined and popularized by James Bach, a founder of the Context-Driven school of testing ([Rapid Software Testing — About the Authors](https://rapid-software-testing.com/authors/), [Satisfice — Exploratory Testing 3.0](https://www.satisfice.com/blog/archives/1509)).
- **Accessibility Tester** — [unsourced — no dedicated source fetched in this pass; role generally understood as specialized testing against WCAG-type standards].
- **Google's historical SET (Software Engineer in Test)** and **TE (Test Engineer)**: SETs were "architects of testability" — building unit test frameworks, refactoring code for testability, and building test automation infrastructure, distinct from TEs' user/product-risk focus ([Google Testing Blog 2013](https://testing.googleblog.com/2013/01/test-engineers-google.html), [Automation Panda — The Software Engineer in Test](https://automationpanda.com/2018/10/02/the-software-engineer-in-test/)). Around 2016 Google restructured: the SET title was phased out in favor of **SETI (Software Engineer, Tools & Infrastructure)**, broadening scope beyond test automation to builds, releases, deployment, metrics, and cycle-time reduction, while TE was retained with an expanded remit (test plans, risk analysis, manual testing) — part of a shift from a "QA" framing to an "Engineering Productivity" framing ([Google Testing Blog — From QA to Engineering Productivity, 2016](https://testing.googleblog.com/2016/03/from-qa-to-engineering-productivity.html)).
- **Microsoft's abolition of the dedicated tester role**: In mid-2014, following a major layoff, Microsoft eliminated the SDET discipline and converted SDETs/SDET Leads to general "Software Engineer (SE)" roles as part of "Combined Engineering" — merging dev and test orgs into one engineering org (e.g., Brian Harry, Visual Studio Team Services: "We combined the dev and test orgs into a consolidated 'engineering' org") ([Pragmatic Engineer — How Microsoft does QA](https://blog.pragmaticengineer.com/how-microsoft-does-qa/), [Mini-Microsoft — 18,000 Microsoft Jobs Gone](https://minimsft.blogspot.com/2014/07/18000-microsoft-jobs-gone-eventually.html)). Reported consequences are mixed and disputed (see Practice variation section).

## Responsibility boundaries

- SET vs TE at Google: testability and long-term test automation infrastructure viability = SET's purview; user impact and overall product/mission risk = TE's purview ([How Google Tests Software, ch.3](https://www.oreilly.com/library/view/how-google-tests/9780132851572/ch03.html)).
- ISTQB Foundation splits duties between **Test Leader** (project management of test activities/resources, evaluation of test object) and **Tester** (test evaluation, defect management, test closure activities, applying test techniques) ([ISTQB Foundation blog](https://istqbfoundation.wordpress.com/2017/09/18/tasks-of-the-test-leader-and-tester/)).
- Context-driven school (Bach/Bolton) treats testing as a skilled investigative activity distinct from scripted execution — the tester's job is to find information about quality via exploration, not merely confirm pre-written expectations ([Rapid Software Testing — What Is Testing?](https://rapid-software-testing.com/what-is-testing-a-conversation-with-james-bach-and-michael-bolton/)).
- Post-2014 Microsoft model collapses the dev/test boundary entirely: developers own unit/integration tests, complex end-to-end tests are reduced in favor of these, and there is no separate "us vs. them" test org ([Pragmatic Engineer](https://blog.pragmaticengineer.com/how-microsoft-does-qa/)).

## Artifacts produced

- **Test plan** — per IEEE 829 (superseded 2013 by ISO/IEC/IEEE 29119), documents scope, approach, resources, schedule, entry/exit/suspension-resumption criteria; formally signed off by stakeholders (engineering lead, product lead, QA lead, plus compliance/security for regulated releases) ([Grokipedia — Test plan](https://grokipedia.com/page/Test_plan), [Coley Consulting — Test Plans and IEEE 829](https://www.coleyconsulting.co.uk/testplan.htm), [Testriq — IEEE 829-Aligned Test Plan Template](https://www.testriq.com/test-plan-template)).
- **Test strategy** — the higher-level, often project/organization-wide document that a test plan operationalizes; consumed by test leads/managers and stakeholders planning coverage approach. [unsourced — distinct source not separately fetched; inferred from test-plan sources' plan/strategy distinction, e.g. Yrkan blog title "Test Plan & Test Strategy: Blueprint for Testing Success"].
- **Test case** — a documented input/action/expected-result unit consumed by testers (manual or automated) executing against the system under test. [unsourced — general ISTQB-adjacent convention].
- **Bug report** — per Mozilla's Bug Writing Guidelines: must contain actual (incorrect) behavior, minimized numbered steps to reproduce, expected correct behavior, and environment details (software version, hardware/OS); severity indicates scope of the bug's effect and is tracked alongside priority so developers can triage ([Mozilla Bug Writing Guidelines](https://developer.mozilla.org/docs/mozilla/qa/bug_writing_guidelines), [Firefox Source Docs — Defect Severity](https://firefox-source-docs.mozilla.org/bug-mgmt/guides/severity.html), [Firefox Source Docs — Triage for Bugzilla](https://firefox-source-docs.mozilla.org/bug-mgmt/policies/triage-bugzilla.html)). Consumed by developers (to fix) and triage/release owners (to prioritize).
- **Test report** — results of test execution consumed by QA leads/stakeholders to judge exit-criteria satisfaction (see Gates). [unsourced — inferred from exit-criteria sources].
- **Coverage report** — [unsourced — no dedicated source fetched this pass].
- **Regression suite definition** — [unsourced — no dedicated source fetched this pass].
- **Release sign-off** — formal approval document/step, typically signed by Engineering Lead, Product Lead, QA Lead, and Compliance/Security for regulated releases, gating whether a release proceeds ([Testriq test plan template discussion of exit criteria/sign-off](https://www.testriq.com/test-plan-template)).
- **Triage log** — the record produced by Bugzilla-style triage process classifying incoming bugs by severity/priority for developer action ([Firefox Source Docs — Triage for Bugzilla](https://firefox-source-docs.mozilla.org/bug-mgmt/policies/triage-bugzilla.html)).

## Handoff points

1. **Developer → QA**: code/build is handed to test with an implicit or explicit entry criterion (build must at least be testable); shift-left practice tries to move testing activity earlier so this handoff happens sooner and more incrementally rather than only at the end of the cycle — a practice traced to Larry Smith's 2001 coining of "shift-left" ([Wikipedia — Shift-left testing](https://en.wikipedia.org/wiki/Shift-left_testing), [GeeksforGeeks — Shift Left Testing](https://www.geeksforgeeks.org/software-testing/shift-left-testing-software-testing/)).
2. **QA → Developer (bug report round trip)**: per Mozilla's guidelines, a bug report that lets a fix proceed without a second conversation must carry (a) precise, minimized reproduction steps, (b) actual vs. expected behavior, (c) environment/version details, and (d) severity classification; incomplete "reproduce occasionally" reports require additional supporting information before they're actionable ([Mozilla Bug Writing Guidelines](https://developer.mozilla.org/docs/mozilla/qa/bug_writing_guidelines)).
3. **QA → Release**: gated by exit criteria evaluated against test reports (tests executed, faults found, fault severity) and formal release sign-off by named stakeholders ([test-plan/exit-criteria sources above](https://www.testriq.com/test-plan-template)).
4. **Contract testing handoff (service boundaries)**: in Pact's consumer-driven model, the consumer team defines expected interactions, generating a contract that the provider team must verify against — a formalized cross-team handoff replacing full integration testing for service boundaries ([Pactflow — What is CDC?](https://pactflow.io/what-is-consumer-driven-contract-testing/), [Pact Docs](https://docs.pact.io/)).

## Gates and decision criteria

- **Entry/exit criteria**: exit criteria define what must be true (tests executed count, faults found, fault severity thresholds) for a test phase to be considered complete and the object releasable; entry criteria define readiness to start testing; suspension/resumption criteria define pause/restart conditions — all standard parts of test planning ([test-plan source above](https://www.testriq.com/test-plan-template)).
- **Release sign-off authority**: typically Engineering Lead, Product Lead, and QA Lead, with Compliance/Security added for regulated releases ([test-plan source above](https://www.testriq.com/test-plan-template)).
- **Canary release as a gate/verification mechanism**: Google SRE describes canarying as a partial, time-limited deployment evaluated before full rollout is allowed to proceed — effectively a production verification gate, distinct from feature flags which are application-level and controlled by app teams rather than infra/SRE teams ([Google SRE Workbook — Canarying Releases](https://sre.google/workbook/canarying-releases/), [Google SRE Book — Release Engineering](https://sre.google/sre-book/release-engineering/), [Harness — Canary Releases and Feature Flags Explained](https://www.harness.io/blog/canary-release-feature-flags)).
- **Chaos engineering as a continuous verification gate**: Netflix's practice (Chaos Monkey, Chaos Kong, FIT, ChAP) formulates hypotheses about steady-state behavior and injects failures in production, with some experiments run continuously as part of the deployment pipeline — a form of ongoing resilience verification rather than a one-time pre-release gate ([O'Reilly — Chaos Engineering](https://www.oreilly.com/content/chaos-engineering/), [LaunchDarkly — Testing in Production the Netflix Way](https://launchdarkly.com/blog/testing-in-production-the-netflix-way/), [Coralogix — How Netflix Uses Fault Injection](https://coralogix.com/blog/how-netflix-uses-fault-injection-to-truly-understand-their-resilience/)).
- **Bug severity thresholds blocking release**: exit criteria commonly combine "number of faults found" and "severity of faults found" as release-blocking thresholds ([test-plan source above](https://www.testriq.com/test-plan-template)); Mozilla's own severity field is explicitly used to triage/prioritize what must be fixed before ship ([Firefox Source Docs — Defect Severity](https://firefox-source-docs.mozilla.org/bug-mgmt/guides/severity.html)).
- **Flaky-test policy**: [unsourced — no dedicated source fetched in this pass].
- **Who can block a release**: converges on the named sign-off stakeholders (Eng Lead / Product Lead / QA Lead / Compliance-Security) rather than any single individual tester ([test-plan source above](https://www.testriq.com/test-plan-template)).

## Practice variation and open debates

- **Dedicated QA vs. developers-own-quality**: Microsoft's 2014 shift eliminated dedicated SDET/test orgs via "Combined Engineering," moving unit/integration test ownership onto developers; reported positive effects include faster shipping (daily releases became possible), improved unit/integration test coverage with fewer complex end-to-end tests, removal of "us vs. them" dynamics, and faster bug feedback loops ([Pragmatic Engineer — How Microsoft does QA](https://blog.pragmaticengineer.com/how-microsoft-does-qa/)). Countervailing reports describe the change pushing testing onto developers who had never done it as part of their job, with some commentary linking this model to quality problems in Windows 10 releases — this specific claim comes from Hacker News discussion commentary, not the Pragmatic Engineer piece itself, and should be treated as anecdotal/disputed ([Hacker News discussion](https://news.ycombinator.com/item?id=19810020), [QA Weekly — How Microsoft went from Test to No Test to Test again](https://qaweekly.substack.com/p/how-microsoft-went-from-test-to-no)).
- **Google's parallel evolution**: rather than eliminating testing roles outright, Google renamed/broadened them (SET→SETI, TE retained/expanded) and reframed the organizing principle from "QA" to "Engineering Productivity," explicitly to let engineers align work with individual strengths/interests while keeping code-writing as a baseline expectation for both tracks ([Google Testing Blog 2016](https://testing.googleblog.com/2016/03/from-qa-to-engineering-productivity.html)).
- **Test pyramid vs. testing trophy**: Mike Cohn's test pyramid (from *Succeeding with Agile*, 2009) prescribes many fast/cheap unit tests, fewer integration tests, and very few slow/brittle E2E tests ([Semaphore — The Testing Pyramid](https://semaphore.io/blog/testing-pyramid)). Kent C. Dodds' "Testing Trophy" inverts the emphasis for frontend work, elevating integration tests as most valuable since modern UIs depend heavily on backend integration and are hard to test in true isolation, de-emphasizing unit tests in favor of static analysis (ESLint, type-checking) at the base ([Baytech Consulting — Test Pyramid vs Testing Trophy](https://www.baytechconsulting.com/blog/test-pyramid-vs-testing-trophy-whats-the-difference), [Smashing Magazine — Long Live The Test Pyramid](https://www.smashingmagazine.com/2023/09/long-live-test-pyramid/)). Broader critique holds the pyramid's strict shape misleads teams into treating test composition as a fixed hierarchy rather than a context-dependent balance ([Medium — Test Pyramid: Foundation or Cage?](https://medium.com/@brijendra.singh/test-pyramid-foundation-or-cage-14187fd59f83), [WireMock — The testing pyramid is an outdated economic model](https://www.wiremock.io/post/rethinking-the-testing-pyramid)).
- **Exploratory/context-driven testing as a school of thought**: James Bach and Michael Bolton's Rapid Software Testing and Context-Driven school treat testing as skilled, non-scriptable investigation; Session-Based Test Management (developed in 2000 by Jonathan and James Marcus Bach) is their proposed way to make exploratory testing auditable/accountable/manageable via chartered, timeboxed sessions with reports ([Wikipedia — Session-based testing](https://en.wikipedia.org/wiki/Session-based_testing), [Rapid Software Testing](https://rapid-software-testing.com/taking-testing-seriously-the-rapid-software-testing-approach/)). This stands in some tension with ISTQB's more standardized, document-driven, syllabus-based model of test management ([ISTQB Advanced Level Test Management syllabus](https://istqb.org/?sdm_process_download=1&download_id=3445)).
- **Contract testing as an alternative to full integration testing**: Pact's consumer-driven contract testing is explicitly positioned as testing only the parts of an API/message interface actually used by consumers, reducing reliance on expensive full integration test environments across service boundaries ([Pactflow](https://pactflow.io/what-is-consumer-driven-contract-testing/), [Microsoft ISE DevBlog — PACT Contract Testing](https://devblogs.microsoft.com/ise/pact-contract-testing-because-not-everything-needs-full-integration-tests/)).
- **Testing in production / canary as a test strategy**: increasingly normalized in continuous-deployment shops; canary releases (infra-level, SRE-owned) and feature flags (app-level, product/eng-owned) are treated as complementary "testing in production" mechanisms rather than substitutes for pre-release testing ([Harness — Canary Releases and Feature Flags Explained](https://www.harness.io/blog/canary-release-feature-flags), [Google Cloud Blog — How release canaries can save your bacon](https://cloud.google.com/blog/products/gcp/how-release-canaries-can-save-your-bacon-cre-life-lessons/)).
- **AI test generation reshaping the role (2025-2026 evidence)**: Industry sources describe a shift from "assistive" AI tools (2024-2025, suggesting test cases/flagging flaky selectors with a human still driving) toward more autonomous "agentic QA" in 2026, where AI agents plan/execute/maintain tests from goals rather than fixed scripts; Gartner is cited predicting 40% of enterprise applications will feature task-specific AI agents by end of 2026 (up from under 5% in 2025), and Deloitte is cited projecting 25% of GenAI-investing businesses will deploy AI agents in 2026, rising to 50% in 2027. Vendor commentary frames this as elevating QA engineers from test executors to "quality strategists and AI orchestrators" rather than eliminating the role outright — this framing comes from vendor/industry blogs (Tricentis, Katalon, Momentic, TestQuality, Parasoft) and should be read as forward-looking industry commentary, not independently verified outcome data ([TestQuality — What Is Agentic QA?](https://testquality.com/the-shift-to-agentic-qa-beyond-automated-testing-to-autonomous-ai-generation-in-2026/), [Tricentis — QA trends for 2026](https://www.tricentis.com/blog/qa-trends-ai-agentic-testing), [Momentic — AI Agents in QA Testing](https://momentic.ai/blog/ai-agents-in-qa-testing), [Katalon — What Is Agentic QA?](https://katalon.com/resources-center/blog/what-is-agentic-qa-the-complete-guide-for-2026), [Parasoft — Top 5 AI Testing Trends for 2026](https://www.parasoft.com/blog/annual-software-testing-trends/)). A separate academic paper questions the actual value of agent-generated tests for LLM-based coding agents, suggesting caution about overstating current effectiveness ([arXiv 2602.07900 — Rethinking the Value of Agent-Generated Tests](https://arxiv.org/pdf/2602.07900)).
